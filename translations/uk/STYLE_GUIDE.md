# Ukrainian Translation Style Guide

## Voice

- Use clear professional Ukrainian.
- Keep a direct engineering tone.
- Preserve the handbook's calm, judgment-oriented voice.
- Prefer reader-facing clarity over literal word-by-word translation.
- Use active voice where it sounds natural.
- Keep paragraphs compact.
- Avoid bureaucratic phrasing and inflated abstractions.
- Avoid Russianisms and calques that make the prose feel translated rather than written.

## Structure

- Preserve the source chapter structure.
- Preserve headings, notebook sections, lists, tables, and artifact shapes unless a phase explicitly approves a publishing adjustment.
- Keep examples attached to the same concept they support in the English source.
- Do not merge or split canonical sections without reviewer approval.

## Punctuation And Typography

- Use Ukrainian quotation marks: «...».
- Use an em dash for sentence-level pauses where Ukrainian prose calls for it.
- Use the Ukrainian apostrophe `ʼ` where appropriate.
- Keep punctuation consistent inside repeated patterns such as review gates, checklist items, and artifact templates.

## Technical Text

- Keep code, shell commands, file paths, commit subjects, IDs, API names, package names, and configuration keys unchanged.
- Do not translate PEAK IDs, chapter IDs, law IDs, artifact IDs, smell IDs, metric IDs, ritual IDs, or failure IDs.
- Do not translate literal command output unless the translation phase explicitly marks it as explanatory prose.

## Terms Usually Left In English

The following terms usually remain in English:

- Principal Engineer
- Staff Engineer
- Senior Engineer
- API
- RFC
- ADR
- CI/CD
- GitHub
- MkDocs
- Vale

If one of these terms needs a Ukrainian explanation, add the explanation in prose while preserving the term itself.

## Preferred Ukrainian Register

- Prefer «рішення» over overly formal alternatives when the sentence means a decision.
- Prefer «обмеження» for constraints.
- Prefer «інженерне судження» for judgment in the engineering sense.
- Prefer «докази» or «інженерні докази» for evidence, depending on context.
- Prefer concrete responsibility language over abstract ownership language.
